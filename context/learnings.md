## १. Service Worker व PWA कॅशिंग शिकवण (PWA & Service Worker Learnings)

### शिकवण १.१: `cache.addAll()` ची ऑल-ऑर-नथिंग (All-or-Nothing) जोखीम
* **समस्या:** `sw.js` च्या `ASSETS_TO_CACHE` यादीत जर एखादी अशी फाईल राहिली जी प्रोजेक्टमधून डिलीट झाली आहे (उदा. `shubham-kharche.html`), तर `fetch()` रिक्वेस्ट 404 रिटर्न करते.
* **परिणाम:** एकही 404 आला तरी `cache.addAll()` पूर्णपणे रिजेक्ट (Fail) होतो. परिणामी नवीन सर्विस वर्कर इन्स्टॉल होत नाही, जुनाच वर्कर चालू राहतो किंवा संपूर्ण ऑफलाइन कॅश कोलमडतो.
* **सर्वोत्तम पद्धत (Best Practice):** जेव्हा जेव्हा प्रोजेक्टमधील फाईल्स डिलीट किंवा रीनेम केल्या जातात, तेव्हा **सर्वप्रथम `sw.js` मधील `ASSETS_TO_CACHE` अपडेट करणे** आणि कॅश व्हर्जन वाढवणे (`anubandh-v48`) अनिवार्य आहे.

### शिकवण १.२: इन्स्टंट लोडिंगसाठी Stale-While-Revalidate धोरण
* **शिकवण:** नेटवर्क-फर्स्ट धोरण इंटरनेट स्लो असताना ॲप अडकवून ठेवते. `caches.match(request)` द्वारे आधी स्थानिक कॅशमधील रिस्पॉन्स १० मिलिसेकंदात युझरला दाखवणे आणि पार्श्वभूमीत सर्व्हरवरून फ्रेश कॉपी डाऊनलोड करणे हे PWA चे सर्वोत्तम धोरण ठरले.

## २. Windows, PowerShell व हेडलेस ब्राउझर शिकवण (Windows & CLI Quirks)

### शिकवण २.१: हेडलेस क्रोम स्क्रीनशॉट व `Access is denied (0x5)`
* **समस्या:** Windows सँडबॉक्समध्ये किंवा थेट `D:\` ड्राईव्हवर `chrome.exe --headless=new --screenshot="D:\...\image.png"` चालवताना क्रोम `Failed to write file: Access is denied. (0x5)` एरर देतो.
* **उपाय (Solution):** क्रोम हेडलेसला नेहमी युझरच्या स्थानिक `%TEMP%` डिरेक्टरीमध्ये स्क्रीनशॉट लिहायला द्यावा (`--screenshot=%TEMP%\image.png`), आणि तिथून फाईल प्रोजेक्ट डिरेक्टरीमध्ये `copy /y` करावी. हा मार्ग १००% वेळेस विनाअडथळा चालतो.

### शिकवण २.२: Windows Batch फाईल्समध्ये `%20` चे अनपेक्षित वर्तन
* **समस्या:** जेव्हा URL मध्ये स्पेससाठी `file:///D:/UBUNTU%20DATA/...` लिहिले जाते, तेव्हा Batch स्क्रिप्ट `%20` ला `%2` (दुसरा कमांड-लाईन पॅरामीटर) + `0` असे समजते. त्यामुळे URL चुकीची होऊन `file:///D:/UBUNTU0DATA/...` बनते व `net::ERR_FILE_NOT_FOUND` एरर येतो.
* **उपाय:** बॅच फाईलमध्ये टक्केवारीचे चिन्ह `%%20` असे दुप्पट (escape) करावे लागते.

### शिकवण २.३: पॉवरशेलमधील स्ट्रिंग एक्सपॅन्शनचे धोके
* **समस्या:** पॉवरशेलच्या डबल कोट्स `"..."` मध्ये जर `$img.Width` किंवा नोडजेएस स्क्रिप्ट लिहिली, तर पॉवरशेल त्या व्हेरिएबल्सचा अर्थ स्वतःच्या शेलमध्ये काढायचा प्रयत्न करतो.
* **उपाय:** थेट लांबलचक इनलाईन कमांड्सऐवजी `scratch/xyz.js` किंवा `scratch/xyz.bat` फाईल तयार करून ती चालवणे अत्यंत सुरक्षित आणि पारदर्शक ठरते.

## ३. Web Share API आणि Clipboard API मधील बारकावे (Mobile vs Desktop Sharing)

### शिकवण ३.१: मोबाईलवर Web Share API सह इमेज फाईल अटॅचमेंट
* **शिकवण:** मोबाईल ब्राउझरमध्ये (Android Chrome, iOS Safari) `navigator.canShare({ files: [file] })` द्वारे खरीखुरी बायनरी इमेज फाईल (`new File([blob], 'name.png', { type: 'image/png' })`) WhatsApp मध्ये पाठवता येते. 
* **फायदा:** युझरला गॅलरी उघडून फोटो शोधण्याची गरज उरत नाही; एका क्लिकवर पत्रिका मेसेजसोबत अटॅच होते.

### शिकवण ३.२: डेस्कटॉपवर क्लिपबोर्ड इमेज फॉलबॅक (ClipboardItem)
* **शिकवण:** डेस्कटॉप क्रोम किंवा व्हॉट्सॲप वेबवर फाईल शेअरिंग चालत नाही. परंतु `navigator.clipboard.write([new ClipboardItem({'image/png': pngBlob})])` द्वारे इमेज थेट रॅम/क्लिपबोर्डवर कॉपी करता येते.
* **सुलभ UX:** युझरला फक्त एक टोस्ट मेसेज दाखवायचा: *"📸 पत्रिका फोटो क्लिपबोर्डवर कॉपी झाला! WhatsApp चॅटमध्ये फक्त Paste (Ctrl+V) करा."* हे वापरकर्त्यांना अत्यंत सोपे वाटते.
* **महत्त्वाचा नियम:** क्लिपबोर्डवर इमेज लिहिताना `image/png` च असावी लागते; अनेक ब्राउझर्स `image/jpeg` क्लिपबोर्ड आयटमला सुरक्षा कारणास्तव परवानगी देत नाहीत.

### शिकवण ४.१: कॅनव्हाससाठी `html2canvas.min.js` स्थानिक असण्याचे महत्त्व

## ७. मल्टी-ॲप व क्रॉस-प्लॅटफॉर्म शेअरिंग शिकवणी (Cross-Platform & Canvas Sharing Learnings)

### शिकवण ७.१: क्लिपबोर्डवर इमेज कॉपी करताना PNG फॉरमॅटची सक्ती
* **तांत्रिक अडचण:** ब्राउझरचा `ClipboardItem` API `image/jpeg` ला अनेक डेस्कटॉप ब्राउझरमध्ये परवानगी देत नाही (NotAllowedError: type image/jpeg not supported on write).
* **उपाय:** जेथे जेथे क्लिपबोर्डवर इमेज टाकायची असते, तेथे इन-मेमरी HTML5 `<canvas>` द्वारे इमेज रेंडर करून `canvas.toBlob(resolve, 'image/png')` मिळवून फक्त `image/png` टाइपच क्लिपबोर्डवर लिहावा लागतो.

### शिकवण ७.२: युनिफाइड व्हिज्युअल ॲसेट (Single Source of Truth)
* **अनुभव:** ॲपमध्ये अनेक ठिकाणी शेअरिंगचे बटणे असतात (कॅन्डिडेट कार्ड, ड्रॉवर, मोडल, बायोडाटा पेज). जर प्रत्येक ठिकाणी वेगवेगळी पद्धत ठेवली, तर एका ठिकाणी लिंक जाते, दुसऱ्या ठिकाणी जुना फोटो जातो, तिसऱ्या ठिकाणी त्रुटी येते.
* **उपाय:** सर्व शेअरिंगचे केंद्रीकरण एकाच पारंपारिक उच्च-दर्जाच्या प्रतिमेवर (`shubham_biodata_redesigned.png`) केल्याने ॲपचा ब्रँड लुक अत्यंत सुसंगत आणि व्यावसायिक बनतो.

### शिकवण ७.३: मोबाइलवर Web Share अयशस्वी होण्याची मुख्य कारणे व ५-टप्पीय तोडगा (Mobile Web Share Pitfalls & Fix)
1. **User Gesture Expiration (वापरकर्ता स्पर्श कालबाह्यता):** मोबाइल ब्राउझर्समध्ये (Chrome on Android / Safari on iOS) `navigator.share()` हे तात्काळ युझर टॅपनंतरच चालवता येते. जर त्यापूर्वी `await fetch()` किंवा `await html2canvas()` सारखे जड ऑपरेशन केले, तर १ सेकंदात ब्राउझरचा गेस्चर टोकन कालबाह्य होतो आणि `NotAllowedError: Must be handling a user gesture to share` फेकली जाते.
2. **Popup Blocker in Mobile:** एकापेक्षा जास्त `await` नंतर `window.open(url, '_blank')` केल्यास मोबाइल ब्राउझर त्याला अनधिकृत पॉपअप समजून ब्लॉक करतो. मोबाइलवर नेहमी `window.location.href = waUrl` वापरावे.
3. **५-टप्पीय मोडल पद्धतीचा विजय:** इमेज आधीच लोड करून **ShareModal** मध्ये प्रिव्ह्यू दाखवणे, आणि मोडलमधील बटणावर क्लिक केल्यावर आधीच तयार असलेल्या `File` ऑब्जेक्टला `navigator.share` मध्ये देणे—यामुळे युझर गेस्चर एका मिलिसेकंदात मिळतो आणि मोबाइलवर शेअरिंग १००% यशस्वी होते.

## ८. माहिती संकलन आणि युझर इंटरफेस सुलभीकरण (UX Simplification & Extensible Data)

### शिकवण ८.१: अवजड CMS ऐवजी जलद की-व्हॅल्यू इनपुट (Key-Value UX Pattern)
* **शिकवण:** जेव्हा युझरला एखाद्या रेकॉर्डमध्ये अतिरिक्त माहिती भरायची असते, तेव्हा त्याला संपूर्ण डेटाबेस स्कीमा किंवा ॲडमिन पॅनलमध्ये नेण्यापेक्षा हलकाफुलका **Key + Value** डायलॉग देणे अत्यंत प्रभावी ठरते.
* **फायदा:** 
  - युझरला आधीपासून ठरवून न दिलेल्या नवीन गोष्टी (उदा. 'कुंडली गुण ३०', 'भाऊ दुबईत असतो', 'स्वतःचा फ्लॅट') कोणत्याही अडथळ्याविना नोंदवता येतात.
  - कार्डावरच ही माहिती स्पष्टपणे दिसते, ज्यामुळे निर्णय घेणे सोपे होते.

## ९. संभाषण मसुदा आणि वैयक्तिकरण (Communication & Personalization Learnings)

### शिकवण ९.१: स्थळांच्या पालकांशी संवाद साधताना आदरातिथ्य आणि सुस्पष्टता
* **शिकवण:** वधूच्या पालकांना मेसेज पाठवताना 'भ्रातृमंडळ वधू-वर सूची', मुलीचे नाव व अ.क्र. अचूक नमूद केल्यास पालकांचा अविश्वास दूर होतो आणि चर्चा सकारात्मक दिशेने सुरू होते.
* **परिणाम:** शुभमचे मुख्य तपशील (शिक्षण, नोकरी, कंपनी, पॅकेज, जन्मतारीख) मुद्देसूद बुलेट्समध्ये दिल्याने वाचकाचा वेळ वाचतो आणि बायोडाटा फोटो व लिंकचे अवलोकन सहज होते.

## १०. स्क्रीनशॉट विरुद्ध घटक कॅनव्हास (Viewport Screenshot vs Isolated Element Canvas)

### शिकवण १०.१: व्ह्यूपोर्ट स्क्रीनशॉटमधील अनावश्यक घटकांचा धोका
* **शिकवण:** हेडलेस क्रोम CLI किंवा साध्या व्ह्यूपोर्ट स्क्रीनशॉटद्वारे (`--window-size`) इमेज तयार करताना ब्राउझरच्या खिडकीतील रिकामी जागा (Body Margins/Padding), पार्श्वभूमी रंग आणि स्क्रीनवर तरंगणारे फ्लोटिंग घटक (उदा. Fixed Action Bar, Share Buttons) प्रतिमेत कॅप्चर होतात.
* **उपाय:** शेअर करण्यायोग्य प्रिंट किंवा पत्रिका निर्मितीसाठी संपूर्ण विंडोचा स्क्रीनशॉट न घेता, केवळ लक्ष्य घटक (`<main class="sheet">`) वेगळा करून `html2canvas` ने रेंडर करावा. तसेच कॅप्चर करताना UI बटणे, फ्लोटिंग बार आणि टूल्स `display: none` करून इमेज १००% स्वच्छ व शुद्ध (Pure Canvas) ठेवावी.

## ११. संदेश आटोपशीरपणा व सुसंगतता (Message Brevity & Clutter Reduction)

### शिकवण ११.१: अनावश्यक तळटिपा (Footers) टाळणे
* **शिकवण:** जेव्हा मूळ संदेशातच संक्षिप्त माहिती, ऑनलाइन बायोडाटाची थेट लिंक आणि संपूर्ण संपर्क पत्ता असलेला पारंपारिक बायोडाटा फोटो सोबत जोडला जातो, तेव्हा संदेशाच्या शेवटी स्वतंत्रपणे कौटुंबिक संपर्क नंबर पुन्हा टाकणे अनावश्यक ठरते.
* **परिणाम:** संदेश `धन्यवाद! 🙏` ने समाप्त केल्याने तो वाचनीय, सभ्य आणि अति-माहितीच्या भडीमारापासून (information clutter) मुक्त राहतो.

## १२. व्हॉट्सॲप डीप-लिंकिंग आणि wa.me सर्वोत्तम पद्धती (WhatsApp Deep-Linking & wa.me Best Practices)

### शिकवण १२.१: `api.whatsapp.com` विरुद्ध `wa.me`
* **शिकवण:** `api.whatsapp.com/send` ही जुनी लेगसी URL पद्धत आहे जी वापरकर्त्याला बऱ्याचदा एका मध्यस्थ वेब पानावर (intermediate redirect landing page) नेते जिथे "Continue to Chat" वर पुन्हा क्लिक करावे लागते.
* **उपाय:** थेट `https://wa.me/<number>?text=<encoded_text>` वापरल्यास अँड्रॉइड व आयफोनवर कोणत्याही मध्यस्थ पानाव्यतिरिक्त तात्काळ मूळ व्हॉट्सॲप ॲप उघडते. नंबर नेहमी आंतरराष्ट्रीय फॉरमॅटमध्ये (उदा. ९१ + १० अंकी नंबर, विना '+' किंवा '-' चिन्हासह) असणे अत्यावश्यक आहे.

## १३. सिंगल सोर्स ऑफ ट्रूथ व DRY तत्त्व (Single Source of Truth: DRY Principle in Messaging)

### शिकवण १३.१: कॉपी-पेस्ट संदेशांचा कोडमधील संसर्ग टाळणे
* **शिकवण:** एकाच मसुद्याच्या स्ट्रिंग्स अनेक वेगवेगळ्या पानांमध्ये (उदा. PWA ॲप, बायोडाटा शीट, स्वतंत्र रीडिझाइन पेज) स्वतंत्रपणे लिहिल्या गेल्यास एखादा बदल होताच कोडमध्ये विसंगती निर्माण होते.
* **उपाय:** सर्व संदेश टेम्पलेट्स एकाच स्वतंत्र जावास्क्रिप्ट फाईलमध्ये (`messages.js`) UMD (Universal Module Definition) पॅटर्नमध्ये ठेवून इतर सर्व फायलींना फक्त त्याचा संदर्भ (reference) द्यावा. यामुळे भविष्यात संदेशात काहीही बदल करायचा झाल्यास **केवळ एकाच फाईलमध्ये एकाच ठिकाणी** बदल पुरेसा ठरतो.

## १४. कॅनव्हास मांडणी आणि व्हिज्युअल बॅलन्स (Canvas Layout & Horizontal Symmetry)

### शिकवण १४.१: डाव्या बाजूस संकुचित डेटा आणि उजवीकडील रिकामी जागा (Right-Side Void) टाळणे
* **शिकवण:** पत्रिकेसारख्या पारंपरिक दस्ताऐवजात जर संपूर्ण शीटची रुंदी (उदा. ८२० पिक्सेल) खूप मोठी ठेवली आणि ग्रिडमधील मजकूर डावीकडेच सीमित राहिला, तर उजव्या बाजूला एक प्रचंड मोकळा पट्टा तयार होतो. हा पट्टा डोळ्यांना खटकतो आणि पत्रिका अधुरी वाटते.
* **उपाय:**
  1. शीटची रुंदी ए४ आस्पेक्ट रेशोनुसार प्रमाणबद्ध (~७२४ पिक्सेल) ठेवावी.
  2. माहितीचा ग्रिड ब्लॉक (`.details-box`) मध्यभागी `max-width: 480px; margin: 0 auto;` ने केंद्रीत करावा, जेणेकरून डावी व उजवी मोकळी जागा तंतोतंत समान (~१२० पिक्सेल) राहून परिपूर्ण सममिती (symmetry) मिळते.
  3. संपर्कांचे तपशील २ ओळींत सुटसुटीत करून पानावर मध्यभागी अलाइन केल्यास संपूर्ण पत्रिकेचा तोल (visual balance) अप्रतिम राहतो.
